# ADR-0004. Оркестрация платежа и доставка вебхуков

**Статус:** принято

## Платёж (payments-service)

- **Конечный автомат** (`payment-status.ts`) — единственный источник допустимых переходов: `created → authorized → captured → refunded`, ответвления `failed` и `canceled`.
- **Намерение фиксируется до побочных эффектов:** платёж сохраняется как `created`, затем вызывается wallet. После сбоя повтор того же запроса дообработает платёж.
- **Ключи вызовов wallet выводятся из id платежа** как HMAC-SHA256 от операции и id платежа с секретом `WALLET_KEY_SECRET`: повтор не удваивает списание, а клиент не может заранее занять ключ.
- **Compare-and-set вместо блокировок на время сети:** `UPDATE … WHERE status = :from`. Проигравший гонку перечитывает состояние; тот же итог — успех, иной — `409`.
- Переход, запись в журнал `payment_transitions` и событие outbox — одна транзакция.
- Бизнес-отказ wallet (нет денег) → `failed` с кодом причины; сетевой сбой → `503` (с id платежа), платёж остаётся `created` и безопасно повторяется. Если клиент не вернулся, платёж доводит фоновая сверка (`PaymentsReconciler`): `authorize` идемпотентен и построен на CAS. `cancel` зависшего платежа сначала довершает авторизацию (иначе холд, созданный без ведома платежа, остался бы замороженным). Счёт мерчанта проверяется до резервирования.

## Вебхуки (notifications-service)

- **Захват пачки** — `UPDATE … FOR UPDATE SKIP LOCKED` с арендой (`next_attempt_at += lease`): HTTP-вызовы идут вне транзакции, упавший воркер не блокирует доставку.
- **Backoff** — экспонента с полным джиттером (`computeBackoffMs`); после `DELIVERY_MAX_ATTEMPTS` доставка уходит в `dead`, доступна в `/deliveries?status=dead` и перезапускается вручную.
- **Подпись** `X-PP-Signature: t=<ts>,v1=<hmac_sha256(secret, "<ts>.<body>")>`; сравнение в постоянном времени, окно 5 минут против replay. Получатель дедуплицирует по `X-PP-Event-Id`.
- **SSRF:** запрещены не-https, localhost, частные сети и редиректы (`redirect: 'manual'`). Остаточный риск — DNS rebinding.
