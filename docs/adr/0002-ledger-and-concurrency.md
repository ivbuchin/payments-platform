# ADR-0002. Двойная запись, деньги и конкурентность в wallet

**Статус:** принято

## Решение

- **Деньги — целые** в минорных единицах: `bigint` в БД и домене, **строка** в JSON и событиях (число теряет точность выше 2^53).
- **Двойная запись:** каждый перевод порождает ровно две проводки (debit/credit) с `balance_after`. Баланс счёта материализован в `accounts.balance`, но всегда равен сумме проводок — это проверяется тестом.
- **Инварианты в БД, не только в коде:** `CHECK (balance >= 0 AND held <= balance)` для пользовательских счетов, `amount > 0`, `from <> to`. Ошибка в логике приложения не сможет увести счёт в минус.
- **Пессимистические блокировки:** счета берутся `SELECT … FOR UPDATE` в порядке `id`. Единый порядок исключает deadlock при встречных переводах (покрыто тестом на 40 параллельных переводов A↔B).
- **Холды** (резервы): `held` уменьшает доступный остаток; capture превращает холд в перевод, release снимает. Переходы финальны и идемпотентны.
- **Системный счёт** валюты — зеркало внешнего мира для пополнений; единственный счёт, которому разрешён минус.

## Идемпотентность

Заголовок `Idempotency-Key` + отпечаток параметров (`sha256`). Быстрый путь — поиск по ключу; гонка двух одинаковых запросов разрешается уникальным индексом: проигравший перечитывает результат победителя. Повтор с другими параметрами — `409`.

## Компромиссы

Пополнения одной валюты сериализуются на блокировке системного счёта. Для масштабирования его можно шардировать (N системных счетов на валюту) — пока избыточно.
